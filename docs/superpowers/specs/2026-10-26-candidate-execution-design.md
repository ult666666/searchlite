## Approaches and scope

Full WAND/MaxScore would need ordered posting cursors, safe numeric upper bounds and a larger execution redesign; it is deferred. A second scoring implementation would undermine existing explanation parity. Choose candidate-aware term-at-a-time scoring: keep existing occurrence tables and global document frequencies, carry a read-only candidate map through existing recursion, and skip score calculation for exclusions. Keep clause evaluation/addition order unchanged. No claim of compressed postings, document-at-a-time/WAND, approximate/vector acceleration, millions-of-documents scale or general latency SLA.

The exact existing public SearchIndex/search/explain/highlight/hybrid/snapshot contracts, tie order and scores remain. No version or release tag change. Tracing continues through the same scorer. Empty intersections may short-circuit because plans were compiled/validated first and execution has no side effects. Exclusions still use the same Boolean interpreter and membership semantics; they just suppress score/trace construction. Current postings/occurrence-table materialization remains a limit.

## Core interfaces and invariants

In src/engine/execute.ts extend internal ExecutionContext with candidates?: ReadonlyMap<number,unknown> and score?: boolean. The map is read-only membership, not relevance/statistics; score defaults true. executeMatch always obtains/caches full occurrences and computes IDF from full occurrence count. Its only-document path also respects candidates. Iterate the smaller candidate/occurrence key set, look up actual frequencies, skip nonmembers, then call the existing scorer. scoreDocument returns an untraced zero hit immediately when score===false, before reading document lengths.

AND executes its first child with inherited context, and subsequent children with the previous survivor map as candidates; it combines maps and scores in the same original child order. Stop after an empty intersection. OR and alternatives inherit candidate restrictions while retaining sum/max semantics. Exclude executes each excluded plan with candidates equal to current hits and score:false, deletes matching IDs, and stops if no hits remain. Never mutate caller candidate maps or occurrence caches. only/trace semantics must remain correct within nested groups.
