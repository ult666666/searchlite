Reviewers can already run an aggregate six-configuration evaluation or type queries in the browser demo, but cannot inspect a configuration change across the judged collection in that demo. ## Approach and boundaries

Extract the six existing configurations and their retrieval logic from scripts/eval.ts into a browser-safe corpus/retrieval.ts module; preserve names, options, transforms, order,100-result depth and the existing eval table. A pure examples/relevance-comparison.ts consumer produces a typed deterministic report by running two selected configurations over all existing queries and composing the unchanged evaluate API. No public library API, ranking formula, judgments, corpus text or existing search behavior changes.

Alternatives considered: another aggregate-only CLI duplicates the existing evaluation table; arbitrary uploaded corpora would create a new ingestion/validation product before solving the visible query-diagnosis gap. The chosen bounded workbench exposes the existing evidence and its limitations in a useful browser workflow. Toy trigram vectors remain explicitly spelling-overlap fixtures, not semantic embeddings or provider integration.

Configuration IDs: bm25f, no-stemming, no-stopwords, no-boosts, single-field, toy-hybrid. Default baseline bm25f, candidate no-stemming. The report schema is searchlite.relevance-comparison/1; JSON includes the full collection inputs/judgments, selected configuration options/identities,100-result depth, per-query rankings with IDs/titles/scores/grades, P@5/R@10/MRR/MAP/nDCG@10, candidate-minus-baseline deltas, missing relevant top10 IDs, and aggregate metrics. MRR/MAP use the full retrieved ranking; P@5 divides by5 even for short runs. Grades absent from a query are treated as0 exactly as in the current collection. Reports carry explicit tiny/single-annotator/fixed-config/toy-hybrid limits and no time, randomness or authenticity claim. Exported input objects are copied, so editing a report cannot alter future runs. Invalid configuration IDs are refused before retrieval.

The native scripts/eval-compare.ts accepts only --baseline=ID, --candidate=ID and standalone --help. Defaults match the page; duplicate/unknown/mixed-help flags exit2 with a bounded usage error, no stack/raw argument echo. Success writes JSON only to stdout through npm run --silent eval:compare. No input files, output-file writes, downloads of models or network calls.

The public demo/relevance.html uses native labelled selects, a swap button, a22-row overview with inspect controls, per-query side-by-side top10 rankings and missed relevant titles, and a download link for the full deterministic report. Keep collection limits and metric cutoffs visible beside results. Share baseline/candidate/query in URL parameters; unknown values show a bounded notice and fall back to defaults. Query selection never changes aggregate/report content. Render text with DOM textContent. Changing either config recomputes rankings and metrics together, including selecting the same config (zero deltas), and updates the download. Native controls and inspect links work by keyboard; mobile tables scroll within their own container without whole-page overflow. Existing demo links to the new page and remains fully usable. Build both pages through Vite's multipage input using existing /searchlite/ base.

Add one pinned development-only Playwright dependency and a real built-page browser journey with an owned loopback server/browser and bounded work/cleanup; no unrelated listener reuse, provider calls, storage or user data. Test configuration/query/swap/reload/invalid URL, actual downloaded JSON parity with the native command, metric/ranking reconciliation, keyboard, narrow viewport, existing search and toy-hybrid disclosures. Run this journey on Ubuntu CI using Chromium. Keep zero runtime dependencies and existing coverage thresholds.
