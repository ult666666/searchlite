# Finite-vector numerical boundaries

Searchlite accepts finite vectors, including very large, very small and zero components. Previously, squaring those values directly could overflow or underflow: aligned vectors near 1e308 produced NaN, aligned vectors near 1e-200 produced zero, and an orthogonal document could incorrectly win top1. A sparse array could also pass validation because Array.every skipped its holes, then fail restoration of the index's own snapshot.

## Calculation and input boundary

The ordinary dot/norm calculation remains the fast path when the dot and norms carry normal finite values and their denominator is finite. The minimum **normal** binary64 value is 2 to the power -1022; Number.MIN_VALUE is instead the smallest positive **subnormal** value. A zero/underflowed/cancelled raw dot or an unsafe norm/denominator uses the fallback.

The fallback divides each vector by its own maximum absolute component. Each scaled component has magnitude at most one, and each nonzero vector has at least one component of magnitude one. Compensated sums accumulate the scaled dot and squared norms. True zero vectors retain cosine zero; two empty arrays retain the standalone function's existing zero convention. The final result is clamped to [-1,1] for rounding drift. Inputs are not mutated.

Scaling to avoid sum-of-squares overflow/underflow is a standard numerical technique; see the primary [LAPACK DLASSQ documentation](https://netlib.org/lapack/explore-html/d8/d76/group__lassq_gae8f40b0a34771b4f2d9c863de3af7be5.html). This JS implementation is independent and does not claim LAPACK equivalence.

The standalone cosine API requires same-length arrays with every component finite. Holes, NaN, infinities and non-array inputs produce the existing INVALID_ARGUMENT error type. SearchIndex vectors remain nonempty and dimension-consistent; the shared validator now visits holes. Bad document additions, atomic batches, replacements, queries and snapshots are refused under their existing error categories without changing the index. Dense zero vectors remain valid.

## Independent reference

The [96-case fixture](../test/fixtures/cosine-reference.json) is generated by a separate [Python standard-library script](../scripts/generate-cosine-reference.py). Decimal.from_float captures the exact supplied binary64 inputs; raw decimal dot products, squared norms and square roots use **3,500 decimal digits**, followed by one conversion to float. It does not reproduce JS scaling or compensated summation.

Cases include zero/empty arrays, largest finite and minimum subnormal components, positive/negative/orthogonal directions, mixed magnitudes, tiny correlations, cancellation, a fixed integer-seeded scale grid, 64-dimensional cases and a wider mixed-scale vector. Inputs are fictional numeric fixtures, with the seed, method and input digest retained. No corpus, embedding model or private data is used.

Tests require finite bounded answers, symmetry and agreement with the reference within an absolute tolerance of 8 × Number.EPSILON. Three tiny nonzero examples also require relative agreement and positive output, so an incorrect zero cannot pass the absolute tolerance. Reversed-coordinate and independent positive-scale checks complement actual hybrid top1/fusion/mutation/snapshot tests.

## Limits

This is finite conformance evidence, not a universally correctly-rounded or exhaustive proof. Near cancellation, relative error can still be large; scaling/compensation do not recover every product or component lost to binary64 rounding. Rounding and clamping can affect near-tie ordering. The ordinary safe path preserves its arithmetic, while previously unsafe cases intentionally change. Exact vector search remains a linear scan; no ANN, inference-quality, production-scale or latency claim follows.

The [candidate-filtering timing receipt](EXECUTION.md) pins its historical engine/module digests. This numerical follow-up changes the bundle and vector behavior; a lexical paired smoke check verifies unchanged lexical results, without relabelling the old timing report as a measurement of this later revision.
